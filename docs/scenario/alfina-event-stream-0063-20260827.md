# 알피나 방 이벤트 스트림 0x63 확인

## 결론

미란다의 집에서 알피나 방으로 이어지는 렌더링 이벤트의 대사는 일반
`Voice/Music/SE` 상위 요청이 아니라 `MUSIC/GR3_STR.IDX`와
`MUSIC/GR3_STR.STZ`의 장시간 스트림을 사용한다.

이벤트 중 활성 EE 오디오 슬롯은 sample `0x414/0x415`를 가리킨다. 두 sample은
동일한 스트림의 좌/우 채널이다.

```text
GR3.IDX sample 0x414/0x415
  -> stream key 0x63
  -> GR3_STR.IDX entry 98
  -> start sector 0x1F391
  -> end sector   0x1FD2C
  -> STZ offset   0x0F9C8800
  -> byte length  0x004CD800
```

스트림 헤더는 다음과 같다.

```text
channels      2
sample rate   24000 Hz
header size   0x800
interleave    0x800 bytes per channel
duration      약 183.531초
```

## 런타임 근거

- 슬롯 4 직전 상태와 유우키가 한숨 쉬는 장면의 상태를 비교했다.
- 이벤트 상태의 EE 일반 오디오 슬롯 `0x001FEA20`은 sample `0x415`였다.
- IOP 스트림 descriptor `0x000A2BF8`의 LSN `0x0016622C`는 ISO의
  `GR3_STR.STZ` LSN `0x00146E9B`에 sector `0x1F391`을 더한 값과 정확히 같다.
- IOP 메모리에 `MUSIC/GR3_STR.STZ` 경로가 열려 있다.
- 일반 상위 Voice/Music/SE 요청 훅은 방 진입 전부터 이벤트 첫 보이스까지 모두
  0회였지만, 공통 하위 오디오 명령 큐는 동작했다.

## 음원 내용 검증

수정한 `audio/scripts/extract_voice.py`로 2채널 블록을 분리해 WAV로 디코드했다.
앞 90초의 자동 일본어 인식에서 다음 알피나 방 대사가 확인됐다.

```text
26.00  とっても素敵な香り
30.00  ああ、ハーブだよ       (자동 인식, 재청취 필요)
35.00  これはカモミール
40.00  …助けてくれてありがとう
42.00  私、アルフィナです
45.00  ああ、お、俺は
47.00  ユウキでしょ？
48.00  ミランダさんが教えてくれたわ
```

타임코드와 문장은 Whisper 초안이라 실제 청취로 다듬어야 한다. 다만 스트림이
해당 이벤트 대사를 포함한다는 판정에는 충분하다.

## 자막 구현 방향

1. 활성 sample `0x414/0x415` 또는 stream key `0x63`을 이벤트 식별자로 사용한다.
2. sample `0x415`가 처음 활성화될 때 60 Hz 전용 타이머를 시작한다.
3. 재생 위치를 기준으로 구간별 한국어 자막을 선택한다.
4. 이미 검증한 pre-SIGNAL VIF/GS 경로로 자막을 매 프레임 출력한다.

한숨 장면 저장 상태는 스트림 시작 약 3초 뒤이며 `0x001FEA30` 값도 `0xB5`, 즉
60 Hz 기준 약 3.02초였다. 저장 상태에서 새 타이머를 0으로 시작해 `1260틱`에 표시한
시험 자막은 실제 스트림 약 24초, `ハーブだよ` 직전에 나타났다. 따라서 훅 호출률은
60 Hz이며, ISO에서 sample 전환 순간부터 시작하는 자기소개 `42~45초` 구간은
`2520~2700`틱이다. 저장 상태 직행 시험에서는 손실된 181틱을 초기값으로 넣는다.
`0x001FEA30` 자체는 스트림 시작마다 0으로 초기화되지 않으므로 일반 재생 위치로 쓰지
않는다. 전용 타이머는 sample이 바뀌면 초기화되며, 게임 일시정지 중에는 렌더 훅도
멈추므로 싱크가 유지된다.

## 긴 문장 및 저장 용량 검증

`어젯밤 도와줘서 정말 고마워요.`를 NanumGothicBold 24px로 래스터화한 뒤,
동일 행 구간을 세로로 병합한 210개 GS 사각형으로 출력했다. 완성된 문장은 화면에서
정상 표시됐으며 40초(`2400틱`)에 나타나 43초(`2580틱`)에 사라지는 것도 확인했다.

매 사각형 묶음마다 중복되던 DMA/VIF/GIF/GS 헤더는 한 번만 저장하고, 각 사각형은
두 XYZ 좌표(8바이트)만 보관한다. 런타임 코드가 4개씩 안전한 15QW 이하 패킷으로
확장한다.

```text
문장 비트맵       318 x 22
사각형 수         210
공통 헤더         112 bytes
사각형 좌표       1,680 bytes
총 저장 데이터    1,792 bytes
기존 완성 패킷식  12,656 bytes (추산)
```

따라서 4글자 제한은 없다. 현재 4KB 데이터 영역에도 이 16글자 문장이 충분히 들어가며,
여러 자막을 넣을 때는 문장별 비트맵을 전부 중복 저장하기보다 글리프 캐시나 외부 자막
테이블을 사용하는 방향이 효율적이다.

최종 타이밍 시험 ISO:

```text
build/event-stream63-long-subtitle-test-v19/
  Grandia3_v19_alfina_long_compressed_subtitle_test.iso
```

ISO는 원본 SLPM 한 항목만 교체했고 역검증을 통과했다. 새 ISO로 오프닝과 타이틀
화면까지 정상 부팅되는 것을 확인했다.

## 다중 자막 시간표 검증

공통 GS 헤더 뒤에 16바이트짜리 큐 레코드와 문장별 사각형 배열을 배치하는 시간표
형식을 추가했다. 큐 레코드는 `시작틱, 종료틱, 사각형 주소, 사각형 수`로 구성한다.
런타임 훅은 현재 60 Hz 타이머가 포함되는 레코드 하나를 찾아 렌더링한다.

18px 글꼴로 다음 다섯 문장을 40~52초에 연속 배치했다.

```text
2400~2520  어젯밤 도와줘서 정말 고마워요.
2520~2700  저는 알피나예요.
2700~2820  아, 나는…
2820~2910  유우키 맞죠?
2910~3120  미란다 씨가 알려주셨어요.
```

전체 데이터는 `4,056/4,096 bytes`, 렌더 코드 동굴은 `668/1,536 bytes`다.
실기 화면 시험에서 다섯 문장이 각각 유지되며 순서대로 전환되고 마지막에 사라지는
것을 확인했다. 첫 구현에서는 렌더 완료 뒤 타이머 초기화 코드로 실행이 떨어져 자막이
한 프레임만 깜빡였으나, 렌더 뒤 복귀 분기를 추가해 수정했다.

다중 자막 시험 ISO:

```text
build/event-stream63-multi-subtitle-test-v19/
  Grandia3_v19_alfina_multi_subtitle_schedule_test.iso
```

ISO 역검증과 실제 GAME ARTS 로고 진입을 확인했다. SHA-256은
`8947c4f653cfc7d27dd523716b52c761d693fc88eaafacb12e06841e51cf65b5`다.

## 실제 폰트 텍스처 렌더링 검증

NanumGothicBold 16px를 EE에서 미리 래스터화한 뒤 GS 로컬 메모리에 업로드하고,
텍스처 스프라이트로 출력하는 경로를 검증했다. 최초 16×16 `가` 한 글자와
256×16 장문 `어젯밤 도와줘서 정말 고마워요.`가 모두 정상 표시됐다.

VIF 경로의 한 패킷은 16QW 이하로 유지해야 한다. 하나의 긴 GIF IMAGE 명령을 여러
VIF DIRECT 커밋에 걸치면 검은 화면이 발생했으며, 각 조각을 독립된 GIF IMAGE
태그로 완결하자 정상 동작했다.

PSMT4 + 16색 알파 CLUT 방식은 2,912바이트로 장문을 4KB 동굴에 넣을 수 있었지만,
게임 렌더링 도중 CLUT가 오염되어 글자가 간헐적으로 여러 색으로 바뀌었다. 따라서
최종 기준에서는 팔레트를 사용하지 않는 PSMCT32 RGBA 텍스처를 사용한다.

RGBA 장문은 완성 패킷 기준 19,104바이트다. 상태저장 시험에서는 EE
`0x01200000`에 주입했으며, 장면 전환 뒤에도 흰색이 안정적으로 유지됐다. 같은
방식으로 아래 다섯 문장을 하나의 시간표로 묶었다.

```text
2400~2520  어젯밤 도와줘서 정말 고마워요.
2520~2700  저는 알피나예요.
2700~2820  아, 나는…
2820~2910  유우키 맞죠?
2910~3120  미란다 씨가 알려주셨어요.
```

전체 RGBA 시간표 데이터는 67,472바이트, 런타임 코드는 516/1,536바이트다.
상태저장 실기 시험에서 다섯 문장이 순서대로 표시되고 모두 흰색을 유지하는 것을
확인했다.

시험 산출물:

```text
build/event-stream63-font-long-rgba-external-v2-test-v19/SLPM_659.76
build/event-stream63-font-rgba-schedule-external-test-v19/SLPM_659.76
/var/tmp/gr3-pcsx2-probe/stream63-font-rgba-schedule-slot1.p2s
```

추가 ELF PT_LOAD 세그먼트는 상태저장 주입에서는 읽히지만 ISO 콜드 부팅 시 게임의
로더가 적재하지 않는다. 따라서 ISO 완성판의 다음 과제는 `GR3_STR.IDX/STZ` 또는
별도 기존 파일을 통해 67KB 자막 패킷 데이터를 EE 메모리로 읽어오는 로더를 연결하는
것이다.

## 전체 이벤트 자막 및 확정 표시 사양

스트림 `0x63` 전체 183.531초를 전사·번역해 49개의 한국어 큐로 구성했다. 원본과
번역, 시작·종료 시각은 다음 파일을 단일 원본으로 사용한다.

```text
data/scenario/alfina_room_event_0063_cues.json
```

49개 자막을 PSMCT32 RGBA 패킷으로 변환한 외부 데이터는 722,096바이트이며,
EE `0x01200000`에 주입한 상태저장 시험에서 전체 이벤트의 번역과 싱크를 확인했다.
상태저장 직행 시험은 전용 60Hz 타이머를 181틱으로 시작해야 실제 음성과 일치한다.

사용자 화면 검증을 거쳐 다음 표시 방식을 이후 렌더링 이벤트 자막의 기준으로
확정했다.

```text
글꼴                 NanumGothicBold
한 줄 글꼴 크기      16px
두 줄 글꼴 크기      14px
두 줄 간격            3px
자막 세로 중심        y=380 (512x448 GS 좌표계)
배경 가로 범위        x=32..480
한 줄 배경 높이       32px
두 줄 배경 높이       48px
배경                  반투명 검정(alpha 0x40)
텍스처                PSMCT32 RGBA, 흰색, CLUT 미사용
```

두 줄 배경 높이는 고정 68px에서 48px로 줄였다. 배경 높이는 텍스처 높이에 16px를
더해 자동 계산하므로 한 줄과 두 줄 모두 같은 상하 여백을 가진다. 검은 테두리를 위해
텍스처를 중복 출력하는 방식은 프레임당 VIF 패킷 수가 커져 검은 화면을 일으켰으므로
사용하지 않는다. PSMT4 팔레트 방식 역시 장면 중 색상 오염이 발생하므로 사용하지
않는다.

검증 산출물:

```text
build/event-stream63-font-rgba-full-event-boxed-v2-test-v19/SLPM_659.76
/var/tmp/gr3-pcsx2-probe/stream63-font-rgba-full-event-boxed-v2-full-slot1.p2s
```

## 콜드부팅용 필드 리소스 적재 방식

원본 `DATA/00030100.MDZ` 뒤에 압축 데이터를 그대로 덧붙이는 시험은 MDZ의 선언된
헤더+페이로드 크기와 실제 파일 크기를 불일치시켜 콜드부팅 검은 화면을 일으켰다.
이 방식은 폐기한다.

대신 MDZ를 MDT로 해제한 뒤 마지막 `0xA0000200` 청크를 정식으로 확장한다. 원래
청크는 decoded MDT 오프셋 `0x002D5480`, 크기 `0x100`이며, 이벤트 중 런타임 주소는
`0x015DC380`이다. 원래 본문 직후 `0x015DC480`부터 101,109바이트 LZ4 블록을 두고,
프레임 훅이 필드 경로와 압축 선두값을 확인한 다음 722,096바이트 RGBA 시간표를
`0x0179C800`으로 한 번만 해제한다.

새 MDZ는 기존 86청크를 유지하며 최종 청크만 `0x18C00`으로 확장한다. ISO에서
역추출한 결과는 decoded 3,072,128바이트, 86청크로 구조 검증됐고 압축 블록과 전체
RGBA 시간표의 왕복도 일치했다. ISO 콜드부팅은 게임 로고 영상 진입까지 확인했다.

```text
Grandia3_KOR_cumulative_v26_alfina_full_subtitles_ko_test_20260827.iso
SHA-256 d06d35fa48ba09e59d171e04d47faad946055f0d5d3a05f574bd83fafdfdca48
build/event-stream63-full-rgba-mdt-chunk-v26/
```

실기에서는 타이틀까지 부팅됐지만 필드 로더가 스트림 `0x40C`의 검은 전환 화면에서
진행하지 못했다. 상태저장 확인 결과 확장 청크와 압축 블록, 722KB 해제 결과까지는
정상이었으므로 청크 크기 확장 자체를 게임의 후속 파서가 허용하지 않는 것으로
판정했다. 따라서 위 v26 방식도 최종 후보에서는 제외한다.

대체 v27은 청크 50(`0xA0001340`) 안의 기존 0 패딩 12,352바이트를 사용한다. 모든
청크 크기와 인스턴스 수, decoded MDT 전체 크기 2,971,008바이트를 원본 그대로
유지한다. 49개 문장을 1bpp 마스크로 압축한 11,362바이트를 런타임 주소
`0x015D2840`에 두고, 훅이 20,400바이트로 해제한 뒤 매 프레임 RGBA 전송 패킷을
동적으로 만든다. 7종의 배경/전송/그리기 패킷 템플릿 3,680바이트는 실행 파일의
검증된 데이터 동굴에 둔다.

```text
Grandia3_KOR_cumulative_v27_alfina_mask_subtitles_ko_test_20260827.iso
SHA-256 4349461d3b17e4d6ad57d9f5a44309a99bb1106d79607a2060aa4d71f94c9dcf
build/event-stream63-full-mask-mdt-padding-v27/
```

사용자 실기에서 v27을 콜드부팅하고 게임 내 메모리카드로 미란다의 집을 불러온 뒤,
방 진입 전 필드 표시부터 스트림 `0x415` 종료 후 필드 복귀까지 확인했다. 49개 자막의
순서, 한 줄/두 줄 표시, 소거, 싱크가 모두 정상이었고 검은 화면이나 진행 정지는
재발하지 않았다. 따라서 **청크 내부 패딩 + 1bpp 마스크 동적 RGBA 전송**을 이후
렌더링 이벤트 자막의 확정 방식으로 사용한다.

v27의 기반은 자막 실험용 v25였으므로, 배 침실·식사 이벤트 전체 번역을 포함한 중앙
v26에 같은 패치를 적용한 누적 v28도 생성했다. 두 기반 ISO에서 `SLPM_659.76`과
`DATA/00030100.MDZ`의 SHA-256이 각각 완전히 같아서, v28의 자막 실행 파일과 MDZ는
실기 통과한 v27과 바이트 단위로 동일하다.

```text
Grandia3_KOR_cumulative_v28_ship_scene_alfina_subtitles_ko_test_20260827.iso
SHA-256 7493d25e8db30806e21d4b12fc8f39e4e73dd8f7fa1e7fadf1b2096a60a25663
build/event-stream63-full-mask-mdt-padding-v28-cumulative/
```

## v29 공통 GR3 이벤트 조회 엔진

v28까지의 런타임 코드는 sample ID `0x415`를 직접 비교했다. v29에서는 이를
`현재 sample ID -> 이벤트 레코드 -> cue table` 조회로 바꿨다. 자막 원본은
`data/scenario/gr3_rendered_event_subtitles.json`에 등록하며, 각 이벤트 레코드는
stream key, 런타임 trigger sample ID, cue JSON, timer bias를 가진다. 같은 음원을
가리키는 sample ID가 여럿이어도 이벤트 타이머의 정체성은 stream key로 유지하므로
sample 전환 때문에 시간이 처음으로 되돌아가지 않는다.

현재 데이터베이스에는 런타임으로 입증된 `alfina_room_0063` 한 건이 들어 있다.
`GR3.IDX` 정적 검증에는 sample `0x414/0x415`를 모두 사용하고, 실제 프레임 훅의
trigger는 관측된 `0x415`만 사용한다. 49개 cue와 1bpp 마스크를 `GR3SUB2` 형식으로
패킹한 뒤 raw LZ4 11,399바이트로 압축하여 기존 청크 50의 검증된 0 패딩에 넣었다.
해제 크기는 20,464바이트이며 기존 decoded MDT 크기와 86개 청크 구조는 유지된다.

누적 v28을 기반으로 만든 v29는 ISO 1,265개 entry 중 아래 두 파일만 달라졌다.

```text
SLPM_659.76
DATA/00030100.MDZ
```

역추출한 MDZ와 빌드 산출물이 일치했고, 해제한 `GR3SUB2` 데이터도 원본 패키지와
일치했다. SLPM 변경 범위도 프레임 훅, 패킷 템플릿 동굴, 렌더러 코드 동굴 세
범위로 제한됨을 확인했다.

```text
Grandia3_KOR_cumulative_v29_gr3_event_lookup_subtitles_ko_test_20260827.iso
SHA-256 e0b6dfec45125c3f9902d4a22086fae496c45f66ed5cba0103e35128247b6a93
build/gr3-event-subtitle-engine-v29-cumulative/
상태: STATIC PASS / RUNTIME PENDING
```

엔진 자체는 여러 이벤트 레코드를 처리하지만 현재 패키지의 리소스 gate와 저장
공간은 `DATA/00030100.MDZ`에 한정된다. 다른 필드 MDZ에서 실행되는 이벤트를 추가할
때는 그 이벤트의 소속 MDZ, 압축 원본 런타임 주소, 안전한 패딩을 먼저 확정해야 한다.
이 세 항목이 확인되면 같은 매니페스트·패커·조회 코드를 그대로 재사용한다.
