# Grandia III 한국어 패치 재패킹·이벤트 자막 재설계 계획

작성일: 2026-09-04

상태: 설계 초안 / GPT 검토용 / 구현 전

## 1. 이 문서의 목적

현재 방식은 새 문제가 발견될 때마다 특정 이벤트를 우회하거나 실행 파일과
`GR3SUB.BIN`을 부분 수정하는 식으로 유지되고 있다. 이 방식은 단기 시험에는 유용했지만,
전체 게임을 끝까지 안정적으로 만드는 방법으로는 비용과 위험이 너무 크다.

이번 재설계의 목적은 다음 세 가지다.

1. CLEAN 원본 디스크의 파일 순서와 물리 위치를 최대한 보존하고, 최종 ISO 용량도
   원본에 가깝게 줄인다.
2. 현재의 렌더링 이벤트 자막 체계와 제작 절차를 한 번에 이해할 수 있게 정리한다.
3. 지금까지 실제로 드러난 멈춤·전환 실패·메모리 충돌 문제를 구조적으로 제거할
   새 빌드 및 자막 구조를 정한다.

이 문서는 과거 시험판 중 하나를 그대로 최종판으로 승격하기 위한 문서가 아니다.
원본에서 다시 만들 수 있는 재현 가능한 빌드 체계를 먼저 세우는 것이 목표다.

## 2. 현재 기준 수치

| 항목 | 바이트 | GiB |
|---|---:|---:|
| CLEAN Disc 1 원본 | 4,598,890,496 | 4.283 |
| 최근 한국어 테스트 ISO | 5,758,263,296 | 5.363 |
| 증가분 | 1,159,372,800 | 1.080 |

현재 이미지는 원본보다 약 **25.2%** 크다. 사용자가 보는 표기에서는 대략
`4.6GB → 5.7GB`에 해당한다.

여기서 “원본과 비슷한 위치”는 다음과 같이 정의한다.

- 같은 파일은 가능하면 원본과 같은 LSN/extent에 둔다.
- 교체 파일이 원래 할당 공간 안에 들어가면 제자리 교체한다.
- 제자리 교체가 불가능한 파일만 이동한다.
- 이동하더라도 원본 파일 순서와 인접 리소스 관계를 최대한 유지한다.
- ISO9660과 UDF가 동일한 실제 데이터를 가리키도록 함께 갱신한다.
- 단순히 ISO 끝에 모든 수정 파일을 계속 붙이지 않는다.

최근 테스트 ISO는 현재 기능을 확인하는 진단 자료일 뿐, 새 레이아웃의 기준 원본으로
사용하지 않는다. 새 정식 빌드는 CLEAN 원본과 승인된 교체 자산 목록에서 생성한다.

## 3. 현재 ISO 제작 방식의 개요

현재 프로젝트에는 두 종류의 빌드가 혼재한다.

### 3.1 전체 재패킹

원본 파일을 풀고 번역된 `MDZ`, 공용 실행 파일, UI, 전투 데이터, 영상 등을 합쳐
ISO를 다시 만드는 방식이다. 크기가 달라진 파일을 쉽게 넣을 수 있지만, 도구가 정한
정렬과 패딩에 따라 많은 파일의 extent가 바뀔 수 있다. 커진 영상이나 리소스가 있으면
그 뒤의 데이터가 연쇄적으로 밀리고, 디스크 끝의 빈 공간과 패딩도 커질 수 있다.

### 3.2 고정 extent 부분 교체

이미 만들어진 ISO에서 대상 파일의 기존 extent에 같은 크기의 바이너리만 덮어쓰는
방식이다. 변경 범위가 작고 검증하기 쉽지만, 교체 파일 크기가 원본과 같아야 한다.
최근 `SLPM_659.76`, `GR3SUB.BIN` 진단판은 이 방식으로 만들었다.

두 방식 모두 쓸 수 있지만, 정식 빌드에서는 **CLEAN 원본의 전체 배치도를 기준으로 한
단일 레이아웃 계획**이 먼저 만들어져야 한다. 이전 테스트 ISO에 다시 덧씌우는 방식은
정식 빌드에서 금지한다.

## 4. 현재 렌더링 이벤트 자막 체계

### 4.1 자막의 원본 음성

렌더링 이벤트 음성은 주로 다음 파일에서 찾는다.

```text
MUSIC/GR3.IDX
MUSIC/GR3_STR.IDX
MUSIC/GR3_STR.STZ
```

`GR3_STR.STZ`에는 2채널 PSX ADPCM 스트림이 들어 있다. 인덱스와 런타임 sample ID를
대조해 장면별 stream key를 찾고, 해당 범위만 FLAC으로 추출해 듣고 전사한다.

### 4.2 이벤트를 식별하는 방법

게임 장면 도중 PCSX2 상태저장 또는 라이브 메모리를 조사해 다음 정보를 모은다.

- 현재 적재된 `DATA/########.MDZ` 경로
- 음성 request slot의 요청 sample과 resolved sample
- 현재 GR3 stream key
- request progress와 이벤트 진행값
- 필요할 때 SPU2의 실제 재생 데이터를 원본 스트림과 대조한 결과

주요 회전 request slot은 `0x00213550`, `0x002135DC`다. 이벤트에 따라 두 슬롯 중
어느 쪽을 사용할지 바뀌므로, 현재 구조는 같은 이벤트에 슬롯별 dispatch 행을 둔다.

### 4.3 전사·번역·싱크 자료

작업 흐름은 다음과 같다.

```text
실제 장면과 런타임 sample/stream 확인
  → GR3_STR 음성 FLAC 추출
  → 일본어 전사와 화자 검수
  → 한국어 번역
  → 시작/종료 시간을 60Hz tick 기준으로 조정
  → stream별 cue JSON 저장
  → 승인 이벤트 manifest에 등록
```

주요 정본은 다음 파일이다.

```text
data/scenario/gr3_rendered_event_subtitles.json
data/scenario/gr3_stream_XXXX_cues.json
audio/transcripts/gr3_rendered_events/
audio/manifests/gr3_stream_inventory/
```

자동 전사는 초안일 뿐이다. 반복음, 무음, 효과음에서는 Whisper 환각이 발생하므로
원음과 실제 장면을 사람이 확인한 cue만 활성화한다.

### 4.4 `GR3SUB.BIN`

현재 일반 렌더링 이벤트 자막은 ISO 루트의 단일 외부 파일 `GR3SUB.BIN`으로 묶인다.
최근 준비본의 규모는 다음과 같다.

| 항목 | 현재 값 |
|---|---:|
| 이벤트 | 63 |
| cue | 741 |
| MDZ 리소스 | 55 |
| 파일 크기 | 190,464바이트 |

파일에는 대략 다음 데이터가 들어 있다.

- 한글 4bpp 글리프 데이터
- 한국어 문장과 cue
- MDZ 경로 dispatch 표 `G3D1`
- resource-local sample/event 조회표 `G3R1`
- 문장 합성 및 렌더링 지원 데이터
- 일부 특수 이벤트용 sidecar 데이터

일반 이벤트 dispatch는 현재 MDZ 경로의 일부 시그니처와 request slot의 sample ID를
함께 사용해 활성 자막을 찾는다. 시간은 가능하면 음성 request progress에 동기화한다.

### 4.5 SLPM 공용 코드

`SLPM_659.76`에는 다음 공용 동작을 위한 훅과 코드 cave가 있다.

- `GR3SUB.BIN` 적재와 무결성 확인
- 현재 MDZ 경로 gate
- request slot 및 sample 조회
- cue 시간 진행
- 한 줄 단위 글리프 합성
- GS/VIF를 통한 자막과 반투명 배경 상자 출력
- 이벤트 종료, 경로 변경, 스킵 시 정리

현재 외부 컨테이너는 EE 메모리 `0x0179C800` 부근에 적재된다. 글자는 한 줄을
`512x16 PSMCT32` RGBA 버퍼로 합성한 뒤 GS 임시 영역에 전송하는 방식이다.

### 4.6 카지노의 특수 처리

카지노는 일반 이벤트보다 복잡하다.

```text
0x71 → DATA/01040902.MDZ의 중간 전환 → 미니게임 → 0x72
```

- `0x71`은 SLPM의 별도 호출 경로와 MDZ 안의 자막 데이터를 조합한 특수 구성이다.
- `0x72`는 두 회전 request slot에 모두 등록해야 실제 자막을 읽었다.
- 전환 직전 자막 수명주기를 잘못 잡으면 미니게임 오브젝트가 생성되지 않고 검은
  화면에서 멈췄다.
- 최종 시험에서는 `0x71` 처리와 `0x72` 두 슬롯 구성을 분리해 정상 전환과 자막을
  확인했다.

카지노 방식은 일반 이벤트 구조의 모범 사례가 아니라, 현재 엔진의 수명주기 문제를
보여 주는 예외 사례로 취급한다.

## 5. 현재 드러난 문제점

### 5.1 ISO가 원본보다 약 1.16GB 커짐

현재 정확한 증가분은 확인됐지만, 항목별 원인은 아직 하나의 감사표로 분해되지 않았다.
가능한 원인은 다음과 같으며 각 항목을 실제 수치로 검증해야 한다.

- 커진 번역 MDZ와 영상 파일
- 전체 재패킹 과정의 정렬 및 패딩 증가
- 원래 공간에 들어가지 못한 파일의 tail relocation
- ISO9660/UDF 이중 메타데이터 재작성 방식
- 실험용 추가 파일 또는 더 이상 쓰지 않는 데이터
- 이전 빌드의 빈 영역을 그대로 보존한 뒤 새 데이터를 다시 뒤에 붙인 경우

원인을 추측으로 확정하지 말고, 원본과 현재 ISO의 모든 entry를 비교해 증가분을
파일 데이터, 정렬 간격, 파일시스템 메타데이터, 미사용 tail로 나눈다.

### 5.2 파일 위치 이동 위험

일반 파일은 ISO9660/UDF 디렉터리의 extent를 따라가지만, 게임 내부에 별도의 섹터
위치나 크기 가정이 숨어 있을 가능성을 완전히 배제할 수 없다. 실제로 번역된
`DATA/00008000.MDZ`는 시나리오 레코드가 원본보다 144바이트 커졌고, 확인 가능한
참조는 보정했지만 카지노 전환 실패의 유력 원인으로 조사된 적이 있다.

따라서 “파일이 열리면 안전하다”를 합격 조건으로 삼지 않는다. 변경 파일 내부 참조,
ISO extent, 실제 장면의 종료와 다음 오브젝트 생성까지 검증해야 한다.

### 5.3 단일 전역 `GR3SUB.BIN` 메모리 충돌

현재 가장 큰 구조적 문제다. `GR3SUB.BIN`을 적재한 EE 영역을 일부 게임 리소스가
자기 작업 공간으로 다시 사용하는 장면이 있다.

실제로 확인된 사례:

- `DATA/00214100.MDZ`에서 GR3SUB 영역이 게임 데이터로 재사용됨
- `DATA/00216000.MDZ`에서도 같은 종류의 소유권 충돌이 확인됨
- 멘디의 `DATA/01080505.MDZ`, stream `0x84`는 자막 활성 상태에서 진행이 정지했고,
  해당 sample 하나를 우회하자 정상 진행됨

즉, 단일 고정 주소에 전체 자막 데이터가 항상 존재한다는 가정이 게임의 실제 메모리
수명주기와 충돌한다. 이벤트를 하나씩 denylist에 넣는 것은 근본 해결이 아니다.

### 5.4 부분 경로 시그니처 충돌

`G3D1` 경로 dispatch는 전체 파일명이 아니라 일부 8바이트 시그니처를 사용한다.
그 결과 `DATA/01080501.MDZ`부터 `DATA/01080505.MDZ`까지가 같은 경로 시그니처를
공유한다.

따라서 SLPM의 경로 gate로 `0x84`만 끄려고 하면 정상인 `0x81~0x83`까지 함께 꺼질 수
있다. 현재는 `G3R1`의 `0x84` sample 레코드 한 개를 sentinel로 바꾸는 정밀 우회를
사용한다. 이 방식은 효과는 있지만 수동 패치에 가깝고 manifest의 의도와 바이너리
상태가 어긋날 수 있다.

### 5.5 이벤트 종료·스킵 수명주기

정상 재생에서는 통과해도 대사를 스킵했을 때 멈추는 장면이 있었다. 카지노에서는
`0x71` 오브젝트가 종료·삭제된 뒤 다음 미니게임 오브젝트가 생성되지 않는 상태도
확인됐다.

현재 엔진은 다음 경우를 모두 별개로 처리해야 한다.

- 음성 자연 종료
- 이벤트 스크립트가 음성을 강제 종료
- 사용자가 대사를 빠르게 넘김
- 이벤트 전체 스킵
- 같은 MDZ 안에서 다음 sample로 즉시 전환
- MDZ 변경과 동시에 미니게임 또는 전투 오브젝트 생성

“자막이 화면에서 사라짐”만으로 정리가 끝났다고 판단하면 안 된다. request slot,
타이머, 적재 marker, 렌더 상태까지 모두 원상 복구해야 한다.

### 5.6 렌더 상태 오염과 성능 저하

과거 시험에서 자막 상자만 나오고 글자가 나오지 않거나, 프레임 저하가 발생하거나,
다른 화면의 얼굴·UI가 깨진 사례가 있었다. 원인은 GS/VIF 상태, 임시 texture page,
shadow 상태 또는 게임의 다음 draw와 충돌하는 렌더 수명주기였다.

현재 합성 방식은 이전보다 안정적이지만, 모든 이벤트와 전환에서 렌더 상태를 완전히
복원한다는 전수 증명은 없다.

### 5.7 SLPM code cave 여유 부족

v1.6.7 계열에서 data cave와 frame cave가 거의 가득 찬 빌드가 있었다.

```text
data cave: 4156 / 4160 bytes
frame cave: 1512 / 1536 bytes
```

이 상태에서 이벤트별 예외 코드를 계속 추가하면 작은 수정도 다른 코드를 밀거나
새 cave를 찾아야 한다. 이벤트별 로직을 SLPM에 계속 누적하면 안 된다.

### 5.8 상태저장에 남는 구 자막 메모리

PCSX2 상태저장에는 당시 실행 중이던 SLPM 코드, `GR3SUB.BIN` 메모리, 완료 marker와
request 상태가 함께 들어 있다. 새 ISO를 넣고 옛 상태저장을 불러오면 새 디스크 파일을
읽지 않고 구 메모리를 계속 쓸 수 있다.

따라서 다음을 구분해야 한다.

- 상태저장 분석: 문제 순간의 증거 확보용
- 새 빌드 검증: PCSX2 완전 종료 후 메모리카드 저장에서 cold boot

이 규칙을 지키지 않으면 수정 성공과 실패를 모두 잘못 판단할 수 있다.

### 5.9 이벤트별 호환성 상태가 한눈에 보이지 않음

현재 manifest, cue, transcript, 여러 빌드 보고서와 사용자 실기 결과가 서로 다른
파일에 흩어져 있다. 어떤 이벤트가 다음 중 어디에 해당하는지 한 표로 판단하기 어렵다.

- 미조사
- 런타임 sample/stream만 확인
- 전사·번역 완료
- 자막 출력 확인
- 정상 종료 확인
- 스킵 확인
- 다음 장면 전환 확인
- 메모리 충돌로 제외

이 때문에 과거 실패 입력을 새 ISO에 다시 넣거나, 정상 이벤트를 불필요하게 끄는 일이
생길 수 있다.

## 6. 새 재패킹 원칙

### 원칙 A — CLEAN 원본에서만 시작

정식 후보는 항상 CLEAN 원본 ISO와 승인 manifest에서 만든다. 진단 ISO에 다른 파일을
덧씌워 새 정식판을 만들지 않는다.

### 원칙 B — 원본 extent 우선

각 교체 파일은 아래 순서로 배치한다.

1. 원본 파일 크기 이내면 같은 extent에 제자리 삽입하고 남는 영역을 0 또는 원본
   패딩 정책으로 채운다.
2. 원본 파일 뒤의 실제 빈 sector까지 포함한 로컬 allocation envelope에 들어가면
   같은 시작 extent를 유지한다.
3. 시작 위치를 유지할 수 없을 때만 별도 relocation 대상으로 분류한다.
4. relocation 파일은 원본 순서를 보존한 전용 tail pool에 모은다.
5. 빌드 종료 후 불필요한 tail과 정렬 공간을 제거할 수 있는지 ISO9660/UDF 구조를
   기준으로 계산한다. 임의 `truncate`는 금지한다.

### 원칙 C — 이동 예산을 수치화

빌드 보고서에 최소한 다음 값을 넣는다.

- 전체 파일 수
- 원본 extent 유지 파일 수와 비율
- 크기만 변경된 파일 수
- 이동 파일 수와 경로
- 이동 거리 sector 합계 및 최대값
- 파일 데이터 증가량
- 정렬·패딩 증가량
- 파일시스템 메타데이터 증가량
- 최종 ISO 증가량

목표치는 원본 조사 후 확정하되, 1차 목표는 “변경되지 않은 파일 100% extent 유지”다.

### 원칙 D — 두 파일시스템 동시 검증

Grandia III 이미지는 ISO9660과 UDF를 함께 사용한다. 교체·이동 파일은 양쪽 디렉터리의
경로, extent, 크기, 역추출 SHA-256을 대조한다. 원래 ISO9660에만 있던 사용자 추가
파일은 그 정책을 보고서에 명시한다.

### 원칙 E — 입력을 잠근다

빌드 입력은 `approved_replacements.json` 같은 단일 manifest로 고정한다. 각 항목에는
경로, 원본 SHA-256, 교체 SHA-256, 크기, 상태, 승인 근거를 기록한다. `build/` 폴더에서
이름이 비슷한 최신 파일을 자동 선택하지 않는다.

## 7. 새 자막 구조의 방향

### 7.1 유지할 것

- GR3 음성의 stream 단위 추출과 FLAC 검수
- 실제 런타임 sample/stream/MDZ 매핑
- stream별 cue JSON과 중앙 manifest
- 한글 4bpp 글리프와 한 줄 합성 방식
- request progress 기반 시간 동기화
- 사전 정적 검증과 cold boot 실기 검증 분리

### 7.2 제거할 것

- 전체 `GR3SUB.BIN`을 항상 하나의 위험한 고정 EE 영역에 상주시킨다는 가정
- 바이너리를 만든 뒤 특정 sample 바이트를 수동으로 sentinel 처리하는 절차
- 이벤트가 늘 때마다 SLPM cave에 예외 코드를 추가하는 방식
- 실패 이벤트를 이유 없이 넓은 MDZ 경로 단위로 비활성화하는 방식

### 7.3 권장 구조

다음 구조를 우선 검토한다.

```text
SLPM의 소형 resident 자막 커널
  ├─ 현재 MDZ 전체 경로 확인
  ├─ 두 request slot 감시
  ├─ 이벤트 시작/종료/스킵 상태기계
  ├─ 작은 인덱스만 상주
  └─ 공용 렌더러와 완전한 상태 복원

디스크의 자막 데이터
  ├─ 중앙 정본 manifest에서 자동 생성
  ├─ 이벤트 또는 안전한 그룹 단위로 작은 page 구성
  ├─ 현재 이벤트에 필요한 cue/문장/글리프만 적재
  └─ 전환 전에 명시적으로 비활성화·해제
```

전체 190KB를 한 주소에 상주시키는 대신, 현재 이벤트에 필요한 작은 데이터만
검증된 scratch 영역에 적재하는 것이 핵심이다.

구현 후보는 세 가지다.

| 후보 | 설명 | 장점 | 위험 |
|---|---|---|---|
| A. 단일 파일 부분 적재 | 큰 컨테이너는 유지하되 인덱스와 현재 event page만 읽음 | 파일 수가 적음 | 게임 파일 API의 seek/부분 읽기 검증 필요 |
| B. 소수 bucket 파일 | 이벤트를 여러 작은 컨테이너로 나눠 현재 bucket만 적재 | 메모리 상한 관리가 쉬움 | ISO 디렉터리와 bucket 교체 정책 필요 |
| C. 이벤트별 sidecar | 각 이벤트에 작은 파일 하나를 둠 | 격리와 디버깅이 쉬움 | 파일 수 증가, 디렉터리 공간·로딩 비용 증가 |

우선순위는 `A → B → C`다. 단, 부분 읽기가 안전하지 않으면 B를 선택한다.
번역 MDZ 내부에 자막 payload를 넣는 방식은 MDZ 크기와 내부 참조를 다시 흔들 수 있으므로
기본안에서 제외한다.

### 7.4 메모리 소유권을 먼저 조사

새 적재 주소를 추측으로 고르지 않는다. 대표 장면의 상태저장과 라이브 메모리로 다음을
측정한다.

- 필드 진입부터 퇴장까지 EE 구간별 변경 빈도
- 일반 대화, 렌더 이벤트, 전투, 미니게임의 소유 영역
- MDZ 변경 때 덮이는 범위
- 1회성 scratch와 장기 상주 영역
- GS local memory page의 장면별 사용 여부

후보 영역은 카지노, 멘디, 전투, 영상 전후에서 모두 살아남아야 한다. 그렇지 않으면
한 개의 전역 주소 대신 이벤트별 동적 적재와 즉시 해제를 사용한다.

### 7.5 이벤트 상태기계

새 커널은 최소한 다음 상태를 명시적으로 가져야 한다.

```text
IDLE
  → PATH_MATCHED
  → SAMPLE_ARMED
  → PLAYING
  → ENDING
  → CLEANUP
  → IDLE
```

`PLAYING`에서는 request progress를 따르되, sample 교체, slot state 종료, MDZ 변경,
스킵 flag 중 하나가 먼저 발생하면 즉시 `ENDING`으로 간다. `CLEANUP`에서는 자막 draw,
timer, event pointer, marker, 임시 버퍼와 GS/VIF 상태를 모두 복원한다. 다음 게임
오브젝트의 생성보다 정리가 늦어서는 안 된다.

### 7.6 전체 경로와 명시적 정책 사용

부분 경로 시그니처만으로 이벤트를 구분하지 않는다. 가능한 경우 전체 정규화 경로의
hash와 stream/sample을 함께 사용한다.

이벤트 정책은 바이너리 사후 수정이 아니라 manifest에 둔다.

```json
{
  "stream": "0x84",
  "resource_path": "DATA/01080505.MDZ",
  "runtime_policy": "DISABLED_MEMORY_COLLISION",
  "evidence": "state3 runtime freeze; bypass runtime pass"
}
```

빌더는 이 정책을 읽어 처음부터 dispatch를 생성하지 않아야 한다.

## 8. 단계별 실행 계획

### 단계 0 — 기준선 동결

1. CLEAN Disc 1과 Disc 2의 SHA-256을 고정한다.
2. 현재 승인된 번역, UI, 전투, 영상, 자막 입력을 목록화한다.
3. 각 입력을 `APPROVED`, `RUNTIME_PENDING`, `DIAGNOSTIC_ONLY`, `REJECTED`로 분류한다.
4. 새 구조가 준비될 때까지 기존 ISO에 우회를 더 넣지 않는다.

산출물 예시:

```text
build/baseline-lock.json
build/approved-replacements.json
```

### 단계 1 — 원본/현재 ISO 배치 전수 감사

1. ISO9660과 UDF 양쪽의 모든 파일 경로, extent, 크기, SHA-256을 추출한다.
2. 각 파일 뒤의 실제 빈 sector와 다음 파일까지의 간격을 계산한다.
3. 원본과 현재 5.7GB ISO를 비교한다.
4. 1.16GB 증가분을 파일 증가, gap, padding, metadata, tail로 분해한다.
5. 위치가 바뀐 파일을 전부 나열한다.

산출물 예시:

```text
build/layout-audit/disc1-original-layout.csv
build/layout-audit/disc1-current-layout.csv
build/layout-audit/layout-diff.json
build/layout-audit/size-growth-attribution.md
```

### 단계 2 — 원본 배치 보존형 planner 제작

1. 교체 manifest와 원본 배치도를 입력받는다.
2. 각 파일을 `IN_PLACE`, `LOCAL_GROW`, `RELOCATE`로 자동 분류한다.
3. relocation은 최소화하고 원본 순서 기반 tail pool에 배치한다.
4. ISO9660/UDF 디렉터리를 함께 수정한다.
5. 충돌, 중첩, 잘못된 크기, 미등록 파일을 빌드 전에 거부한다.

### 단계 3 — 동일 데이터로 용량 비교 빌드

기능을 더 추가하지 않고, 현재 승인 입력만 사용해 다음 두 이미지를 비교한다.

- 기존 방식 재패킹본
- 새 원본 배치 보존형 빌드

비교 항목은 ISO 크기, 이동 파일 수, extent 유지율, xdelta 크기, 역추출 해시다.
새 방식이 기능적으로 동일하면서 배치와 용량이 개선돼야 다음 단계로 간다.

### 단계 4 — 자막 메모리 소유권 감사

최소 시험 장면:

- 카지노 `0x71 → 미니게임 → 0x72`
- 멘디 `0x7E`, `0x80~0x86`
- 충돌이 확인된 `0x91`, `0x92`, `0x93`, `0xD4`
- 일반 필드 대화에서 렌더 이벤트 진입/복귀
- 전투 진입/종료

각 장면에서 EE/GS 메모리의 변경 범위와 자막 데이터 수명을 기록한다.

### 단계 5 — 분할 적재 자막 prototype

1. 이벤트 1개만 넣은 최소 page로 시작한다.
2. 정상 재생, 초반/중간/끝 스킵, 다음 장면 전환을 검사한다.
3. 카지노와 멘디를 통과할 때까지 이벤트 수를 늘리지 않는다.
4. 통과 후 5개, 20개, 전체 순으로 확장한다.
5. 이벤트 추가가 SLPM 바이트 수를 늘리지 않는지 확인한다.

### 단계 6 — 이벤트 호환성 행렬 구축

모든 활성 이벤트에 다음 열을 둔다.

```text
event / stream / sample / MDZ / transcript / translation / cue
normal_play / skip_early / skip_mid / skip_late / exit_transition
memory_owner_check / renderer_restore / runtime_status / evidence
```

하나라도 `FAIL`이면 정식판에서 자동 제외하며, 이유 없는 경로 단위 광역 제외는 하지
않는다.

### 단계 7 — 전체 누적 ISO와 회귀 시험

1. CLEAN 원본에서 한 번에 빌드한다.
2. 모든 entry의 ISO9660/UDF extent, size, SHA-256을 역검증한다.
3. 변경 허용 목록 밖 바이트가 바뀌지 않았는지 검사한다.
4. 메모리카드 저장으로 cold boot한다.
5. 카지노, 멘디, 전투, 여관, 필드 이동, 영상 전후를 우선 회귀 시험한다.
6. 통과한 빌드만 버전 번호를 붙이고 xdelta를 만든다.

## 9. 합격 조건

### 9.1 재패킹

- 변경되지 않은 파일의 extent 유지율 100%
- 변경 허용 목록 밖 파일 SHA-256 일치
- ISO9660/UDF의 경로, extent, 크기 일치
- relocation 파일 0개가 이상적이며, 발생 시 모두 이유와 위치 기록
- 최종 ISO 크기 증가분을 항목별로 100% 설명 가능
- 원본보다 커지는 경우에도 “왜 필요한지” 설명되지 않는 padding/tail 0바이트

### 9.2 자막

- 활성 이벤트마다 정상 재생과 스킵 3종 통과
- 이벤트 종료 후 다음 게임 오브젝트가 정상 생성됨
- request slot과 자막 timer가 종료 후 남지 않음
- 다른 MDZ가 자막 메모리를 덮어도 게임이 멈추지 않음
- 얼굴, UI, 전투, 미니게임의 GS/VIF 출력에 잔류 영향 없음
- 이벤트 수 증가로 SLPM cave 사용량이 증가하지 않음
- 제외 이벤트는 manifest에 이유와 증거가 기록됨

## 10. 당장 보존해야 할 현재 사실

- `0x7E`는 문제 이벤트로 확인되지 않았으며 활성 상태가 맞다.
- `0x84`는 `DATA/01080505.MDZ`에서 자막 경로를 우회했을 때 정상 진행됐다.
- `0x84`만 끄기 위해 `010805` 경로 전체를 막으면 안 된다.
- 현재 보수적으로 비활성화된 후반 stream은 `0x91`, `0x92`, `0x93`, `0xD4`다.
- `0x80` 슈미트 첫 만남은 18 cue, `5.9~113.65초` 전체 자막 검수본이 준비돼 있다.
- 카지노는 `0x71`과 `0x72`를 같은 일반 경로로 취급하면 안 된다.
- 옛 PCSX2 상태저장은 새 ISO의 자막 엔진 검증 근거로 사용하면 안 된다.

이 사실들은 새 구조를 설계할 때의 회귀 시험 입력이다. 현재의 sentinel이나 path hash
패치 자체를 새 구조에 그대로 복사하라는 뜻은 아니다.

## 11. GPT에 요청할 핵심 검토 사항

1. 원본 ISO의 extent를 최대한 유지하면서 ISO9660/UDF를 함께 갱신하는 배치 planner의
   안전한 알고리즘을 설계할 것.
2. 5.7GB 이미지의 증가분을 파일 데이터, gap, padding, metadata, tail로 정확히
   귀속시키는 감사 도구를 설계할 것.
3. 전체 `GR3SUB.BIN` 상주 없이 현재 이벤트 page만 적재하는 A/B/C안 중 실제 PS2
   환경에서 가장 단순하고 안전한 구조를 선택할 것.
4. 이벤트 시작·자연 종료·강제 종료·스킵·MDZ 변경을 다루는 상태기계를 검토할 것.
5. SLPM code cave를 더 소비하지 않고 이벤트를 늘릴 수 있는 데이터 주도 dispatch를
   설계할 것.
6. 카지노와 멘디 사례를 반드시 통과해야 하는 회귀 시험으로 고정할 것.
7. 구현 전에 필요한 추가 메모리 관측과 파일 API 역분석 항목을 구체적으로 제시할 것.

## 12. 이번 재설계에서 하지 않을 것

- 문제가 생길 때마다 임의의 이벤트를 하나씩 계속 끄기
- 최신처럼 보이는 `build/` 파일을 이름만 보고 자동 채택하기
- 진단 ISO 위에 다시 진단 ISO를 누적해 정식판 만들기
- 크기 변경 MDZ의 숨은 참조를 확인하지 않고 삽입하기

전부 설명할 수 있으며 이벤트를 추가해도 같은 종류의 멈춤이 반복되지 않는 빌드다.
